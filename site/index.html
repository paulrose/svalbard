01 / The approach

Useful by design.
Quiet by default.

A backup tool has one job to earn your trust.
Here’s how we want to earn it.

[01]

Your database comes first.

Bounded snapshots, one worker by default, and an exit when a backup gets in the way. Close the database snapshot before the upload begins.

Careful by design. Never zero impact.
[02]

Bring your own everything.

Start with PostgreSQL or MySQL. Send backups to S3, R2, or your own SSH server. Separate adapters make room for what comes next.

Your infrastructure. Your keys.
[03]

A terminal is all you need.

Readable configuration. Secrets from your CI environment. Predictable exit codes. A shared GitHub Action is on the map, too.

No dashboard required.

Early days. Deliberate steps.The CLI currently supports help and version output. Backups, adapters, and the Action are still ahead. Restore follows the backup release.

01Getting startedAvailable now+

The repository is private while the foundations take shape. With repository access and Rust installed, build the current CLI: 

cargo build --locked --release
./target/release/svalbard --help
./target/release/svalbard --version

No backup command is available yet. The animation above is a product preview.

02Configuration & secretsPlanned+

One configuration file for the backup job. Environment variables for credentials. Clear precedence, early validation, and redacted diagnostics.

The configuration format is still being designed. Examples will land here with the implementation.

03Database adaptersPlanned+

PostgreSQL and MySQL come first. Each adapter will use the database’s native dump tools and enforce its own safety checks.

MySQL support starts with InnoDB. PostgreSQL needs care around schema changes. Replicas are preferred, and a snapshot must close before storage transfer starts.

04Storage destinationsPlanned+

Amazon S3, Cloudflare R2, and SSH destinations through SFTP or SCP. The adapter boundary keeps destination-specific behavior out of the backup pipeline.

Incomplete uploads must never be reported as successful backups.

05CI & GitHub ActionsPlanned+

Run the CLI directly from a scheduled job, or use a shared, versioned GitHub Action. Both will use the same configuration and secret handling.

Expect noninteractive execution, machine-readable output, and exit codes your pipeline can act on.

06Restore & recoveryUp next+

A native restore command follows the backup release. Before that release, real dumps must pass restore tests with the database’s own tools.

A backup only earns its name when the data can come back.

03 / A name with a purpose

Far north.
Thinking ahead.

Between mainland Norway and the North Pole lies Svalbard: an Arctic archipelago whose name means “the land with the cold shores.”

Inside one of its mountains, the Global Seed Vault keeps backup copies of the world’s crop seeds. A reserve for the days when the original is no longer enough.

That’s the idea we’re borrowing. Keep a copy. Keep it somewhere you trust. Make it possible to start again.

The name travels north. Your data goes wherever you choose.

Built in the open. Soon.
